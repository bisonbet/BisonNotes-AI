## Demonstrated gaps and fixes

### Acknowledgement ownership and stale completion

`PendingCloudMutation` now carries a local-only `acknowledgementID` inside the
existing payload. A new enqueue receives a new fence even when its stable kind,
target, timestamp, and payload are equal to the row already being uploaded.
Store binding preserves the fence. `removeIfUnchanged` requires both semantic
mutation equality and the fence, and the flush/backup paths pass the exact
mutation snapshot they submitted instead of reconstructing one later.

This preserves the existing coalescing and timestamp semantics while ensuring
an older completion cannot erase newer local intent.

### Failed reads and local acknowledgement failures

Critical outbox reads now throw on missing context, failed fetch, or incomplete
legacy migration. The throwing reader is used by pending-mutation flush,
backup selection, and legacy-summary publication; the forgiving wrapper remains
limited to status/UI queries. An unreadable outbox therefore cannot look like an
empty queue and cannot authorize a cloud write or deletion.

After CloudKit accepts a mutation, a failed local acknowledgement now surfaces
as an error and leaves the durable row queued. Partial batches acknowledge only
the exact rows that completed. Legacy relationship cleanup no longer swallows a
failed local save, so its mutation remains retryable. A DEBUG-only save-failure
seam exercises this boundary without affecting production behavior.

### Restore, deletion, conflict, and media safety

Deletion-target reads in the affected cloud paths no longer use `try?` fallbacks
that could turn a network/account/read failure into “no tombstones.” Metadata
scans request recording metadata keys without downloading audio; media remains
subject to the existing staged/readable/identity rules. Existing stable-ID,
timestamp, revive, conflict, no-overwrite, and “Keep on This Device” decisions
were retained rather than replaced.

Failed reads, unavailable media, account/network failures, incomplete query
pages, and untrusted manifests stop the relevant operation or retain the item;
none authorizes destructive cleanup. C’s non-runnable uncertain job attempts
and D’s receipt ownership, retained committed identities, and no-overwrite
publication were not modified.

## Review corrections

- Direct deletion now submits the captured outbox snapshot's child IDs,
  recording association, and original deletion time. Acknowledgement uses that
  same snapshot/fence. Explicit snapshots with the wrong kind or target throw
  before a cloud call. Imported-audio tombstones also use the captured time.
- Outbox binding is throwing. Source-read, destination-copy/save, invalid
  context, and incomplete legacy-migration failures stop flush before cloud
  work. App startup withholds initialization when binding fails; sync cannot
  silently proceed with a previous store. Source cleanup after a successful
  durable copy remains retryable and cannot undo destination commitment.
- Default-zone query fallback now collects all continuation pages, preserving
  desired keys and propagating any later-page or record failure. The extracted
  main-actor pagination helper permits deterministic multi-page/error tests
  without fabricating opaque CloudKit cursors or contacting CloudKit.

New tests verify a direct deletion with merged child IDs and an older queued
request time, a failed destination outbox copy causing zero cloud writes while
retaining source intent, and 2,001 query results across three pages plus a
later-page failure. These are fixture boundary tests, not physical relaunch or
live CloudKit qualification.

During review validation, initial builds caught a missing actor annotation on
the generic page callback and callers needing `try` after the binding signature
change. Those were corrected. The next action passed 249 tests and failed only
a new fixture's incorrect recording-marker prefix; the assertion now uses the
verified production `backup_deletion_` prefix.
