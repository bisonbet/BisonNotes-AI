## Goal

Remove superseded, statically unreferenced code in small reviewable packages while preserving current behavior, stored user data, upgrade compatibility, iCloud behavior, and active provider/transcription paths.

This plan is deliberately narrower than `docs/code-quality-cleanup-delegation-plan.md`. It does not authorize a persistence redesign, provider removal, migration retirement, or error-handling redesign.

## Evidence levels

Use these labels in every package report:

- **Confirmed static candidate**: no production, test, Watch, extension, preview, or conditional-compilation caller was found in the reviewed tree. It may be removed only after the executing agent repeats the search and compiles all affected targets.
- **Live/protected**: a caller, persisted-data path, migration, or runtime side effect exists. Do not remove it under this plan.
- **Decision required**: the path is unreachable or poorly shaped today, but deletion would choose product behavior. Do not implement it without explicit user direction.

“No callers found” is never described as runtime proof. SwiftUI entry points, Objective-C selectors, notifications, App Intents, Codable compatibility, target membership, and persisted filenames can escape a simple reference count.

## Non-negotiable safety rules

1. The lead records `git status --short --branch`, `git rev-parse HEAD`, `git branch --show-current`, and `git worktree list --porcelain` before delegation and again before final handoff.
2. Continue only on `v2.4`. If another branch is active, stop; do not switch or create a replacement branch without user direction.
3. If a required file has unrelated edits, stop that package and report the overlap. Never stash, reset, discard, or absorb another agent's work.
4. Search the entire repository Swift tree, including app tests, UI tests, Watch code, extensions, previews, and `#if` branches, before removing each declaration.
5. Exclude generated artifacts such as `SwiftLintBaseline.json` from caller evidence.
6. Do not edit `project.pbxproj` merely because a source file is removed. The app source uses synchronized filesystem groups. Edit target metadata only if current Xcode evidence proves it is required and the existing project-file owner approves the overlap.
7. Do not combine cleanup with formatting, renaming, architecture changes, prompt changes, provider behavior changes, or data migration changes.
8. One agent owns one file at a time. `SummaryManager.swift`, `DataMigrationManager.swift`, `CoreDataManager.swift`, `AppDataCoordinator.swift`, and `PerformanceOptimizer.swift` are single-owner files.
9. Integrate and validate one package before beginning a dependent package. Do not accumulate one approximately 3,000-line deletion diff.
10. Do not regenerate the SwiftLint baseline. Record pre-existing lint output separately from new violations.
11. No commit, push, PR, history rewrite, or release action is authorized by this document. If commits are later authorized, use one logical commit per accepted package.

## Package H — Decision-required follow-ups, not deletion work

The executing agent investigates and reports these items but makes no source change without an explicit product decision.

### H1 — “Coming soon” engine state

`AIEngineType.isComingSoon` returns `false` for every current case, so the AI Settings coming-soon presentation is unreachable. Separately, `SummaryManager.getComingSoonEngines()` labels all unavailable engines as coming soon and is still called by verbose initialization logging.

Choose one future task:

1. Preserve the state as an intentional future engine contract and add a comment/test explaining it; or
2. Remove the property, status field, unreachable UI branches, verbose log, and now-unused helper atomically.

Do not conflate “unavailable because unconfigured” with “coming soon.”

### H2 — iCloud conflict strategy

`conflictResolutionStrategy` is currently a private constant set to `.newerWins`. The `.deviceWins`, `.cloudWins`, and `.manual` switch branches cannot be selected through current production settings; therefore `pendingConflicts` normally cannot be populated, even though Settings renders manual conflict controls.

Choose one future task:

1. Keep and expose a tested strategy setting; or
2. Standardize on newer-wins and remove the unreachable enum cases, pending-conflict UI, and resolver surface atomically.

Either choice requires focused CloudKit regression coverage and manual two-device conflict validation. This cleanup plan does not choose iCloud policy.

### H3 — EnhancedErrorHandler ownership

Current call sites create throwaway `EnhancedErrorHandler()` instances. Their published alert/history state is discarded, but logging and diagnostic/recovery work still runs.

Choose one future task:

1. Introduce a retained owner and intentionally surface alerts/history; or
2. Replace throwaway handlers with a tested stateless logging/diagnostic service and remove unused UI state.

Do not simply delete private recovery paths while live handlers call them.

### H4 — Launch migration retirement

Migration functions are invoked from app initialization, but most return quickly after versioned UserDefaults guards. Keychain migration intentionally scans remaining legacy settings, and llama.cpp disk cleanup intentionally retries failed file deletion. The v2.4 llama/MLX migrations are current-release compatibility code.

Retire a migration only after the owner defines and documents the minimum supported upgrade version, proves no supported installation can still contain that data, updates migration tests, and removes the migration call, body, keys, alerts, and obsolete fixtures in one reviewed package. Do not remove migrations merely to reduce launch-time call count.

### H5 — `.location` sidecars

The file fallback remains live and new recording paths still write sidecars. A future retirement requires a versioned, resumable migration into Core Data, unresolved-file reporting, tests for old recordings, and a support-floor decision. No `.location` deletion is authorized here.
