# v3.0 Reliability Hardening Plan

## Status and scope

**Status:** reviewed against source on 2026-09-12; implementation and runtime qualification are pending. This document specifies intended behavior, not proof that the behavior exists.

- **Implementation branch:** `v3.0-reliability-hardening`.
- **Verified base and review HEAD:** `3ca03433489bf5d4401125c5e57bdb644a05d45e`, also the local `v3.0` tip at review time. There are no committed differences from that base. The plan was the only untracked file before this review.
- **Reference only:** local `v3.0-sqlitemigration` at `b5c89bff9083c48b692a1f82e1544d7b73a86625`. Recheck these refs before implementation; do not switch, reset, merge, or cherry-pick the reference branch wholesale.
- **Persistence authority:** local Core Data through `NSPersistentContainer`, with application-managed CloudKit synchronization. This is **not** `NSPersistentCloudKitContainer` automatic mirroring.
- **Authorized deliverable for this review:** update this plan only. Implementation, commit, push, and PR creation are separate actions.

Improve preservation of recordings, imported media, transcripts, summaries, and processing jobs when storage, save, file operations, app execution, or CloudKit work fails. Keep the existing Core Data model and custom sync architecture unless a narrowly justified additive change is needed for an invariant below.

### Non-goals

- No GRDB, second metadata backend, Core Data-to-SQLite cutover, migration UI, backend-swapping scaffolding, or migration-only media journal/root registry.
- No new portable export/restore format, encryption/key-management system, or replacement for Apple backups.
- No blanket repository rewrite, persistent-history subsystem, global maintenance lock, or cleanup campaign.
- No deletion of existing migration/recovery code or documentation merely because its name includes “migration.” Existing Core Data model upgrades and legacy-data migrations remain required.

Core Data can itself use a SQLite store; the prohibition is on a new application-managed SQLite backend, not that existing store format. Preserve current file protection, entitlements, sync exclusions, and backup eligibility. OS encryption and backup availability depend on device/account configuration; neither custom CloudKit sync nor a successful local save proves a complete backup.

## Invariants and transaction rules

1. **Unavailable is not empty.** Store-load/fetch failure must be distinguishable from a successful empty result. No failed read may authorize deduplication, orphan deletion, sync reconciliation, or a “saved” acknowledgement.
2. **Success means a completed durable local save.** An allocated UUID, managed object, parent-context merge, UI update, or dispatched task is not acknowledgement. If child contexts are introduced, saving a child is insufficient until the store-writing parent saves successfully.
3. **Filesystem and Core Data are separate transactions.** File publication and metadata save cannot be treated as one atomic transaction. Use a recoverable ordering and stable operation identity, and test the gaps between steps.
4. **Retain a recoverable copy until commitment.** Do not delete an owned source, acknowledge Watch delivery, consume an inbox receipt, or discard recording recovery tracks until the required file and metadata are committed. External/provider temporary URLs may expire; acquire an app-owned durable copy while access is valid. Never delete the user's external original as import cleanup.
5. **Retry is idempotent locally.** Reuse a stable operation/record identity across retries and acknowledgements. Filename equality alone does not establish identity. An intentional rerun is a new attempt, not a duplicate delivery.
6. **Deletion has durable intent.** Save local changes and cloud intent together where required. Retry failed post-save file cleanup without resurrecting deleted content. Do not roll back a committed deletion just because a later filesystem or network step failed.
7. **Isolation includes failure handling.** Keep managed objects on their context queue/actor; pass IDs or value snapshots across boundaries. A rollback affects the whole context: isolate an operation's edits or prove no unrelated edits are pending before rolling back. A later save must not accidentally commit previously failed/disowned work.
8. **Recovery never assumes remote exactly-once execution.** A provider may have accepted a request before termination. Preserve a received result durably where needed before applying it; avoid automatic repeat requests with uncertain outcome unless the retry policy explicitly permits them. Local deduplication does not guarantee no duplicate remote processing/cost.
9. **Cleanup requires ownership and positive evidence.** Limit to app-owned roots, reject escaped paths/symlinks where relevant, protect active operations and referenced media, and treat unreadable/unavailable storage or an external volume as uncertainty. Age alone is not proof that a file is disposable.

### Mechanical enforcement

- Change the existing read/write signatures so compilation enumerates callers; merely adding unused throwing siblings is insufficient. Existing throwing diagnostic fetches and CloudKit's `recordsOrThrow()` demonstrate the error-propagation pattern, but do not mechanically enforce adoption in other paths.
- Remove storage-error-to-empty fallbacks from critical callers. Do not resolve compiler errors with `try?`, `catch { return [] }`, or fabricated success. UI may retain a previously loaded snapshot while showing failure; it must distinguish stale/failed data from a successful empty fetch.
- Keep a caller matrix for runtime entry points, context ownership, and side effects the compiler cannot prove. Check direct fetch/save bypasses and use failure tests at cleanup, sync, and acknowledgement boundaries.
- Map every invariant to its enforcing method/state transition and a failing-path test in the slice report. Type checking helps discover callers; it does not prove transactional or filesystem correctness.

### Compatibility decision before recovery work

Slices A, B1, and B2 must not change the Core Data model. Before C/D introduce durable state, record a decision in the Phase 0 report: reuse existing fields, use a justified operation receipt, or make an additive model change. Specify old/new reader behavior, raw-value compatibility, artifact ownership, cleanup, and rollback tests **before** editing the model or receipt format. Do not overload unrelated fields just to avoid a model version.

No blanket decision that v3.0 can never change its model is made here. An additive change must identify the otherwise unsolved crash gap and its upgrade/rollback implications before implementation. Unchanged schema alone does not make rollback safe: files, cloud effects, and values interpreted differently by an older app still require qualification.

### Phase 1 — Storage readiness and safe launch

- Implement `PersistenceStoreState` with loading, ready, explicitly ephemeral, and unavailable states. `PersistenceStoreFailure` retains sanitized domain/code/underlying causes; `PersistenceReadiness` publishes state on the main actor after store loading completes. `requireDurableStore() throws` rejects every state except ready at production service boundaries. Explicit preview/test access is configured separately; never broaden the production check to permit ephemeral storage. Retain the existing store-loading API unless a change is justified by evidence.
- Remove automatic production in-memory fallback. Preserve the original store and sidecars; do not delete, replace, reset, or automatically rebuild them on error. A genuinely new installation may create its normal store, but a failed open must not be reinterpreted as a new installation.
- Gate construction/start of persistence-dependent managers, migrations, processing, imports, cloud reconciliation, and cleanup until store readiness is established. Audit every entry point in the Phase 0 matrix; UI checks are not a substitute for mutation-level enforcement.
- Provide an accessible storage-unavailable screen with a concise reason and non-destructive retry/relaunch guidance. Use controlled relaunch as the initial recovery action; do not add in-process store replacement in slice A. Any later in-process retry must rebuild/rebind the dependency graph and reject stale callbacks from the failed storage generation.
- Keep optional repairs outside the ready transition, bounded and independently retryable. Never set a migration-complete flag before its own required saves succeed.
- Retain error domain/code and a sanitized underlying-error chain. Do not log raw `NSError.userInfo`, transcript contents, credentials, or unredacted paths as routine diagnostics.

**Tests:** valid existing store; successful new store; invalid/unavailable test URL; deterministic load failure; explicit ephemeral test mode; repeated failure/relaunch; no fallback store; no startup cleanup/sync/write while unavailable. Verify an existing fixture library remains intact after a failed attempt and subsequent successful reopen. Classify disk-full/protected-data failures using injected errors; verify actual platform behavior later on disposable data.

Tests must inspect `persistentStoreCoordinator.persistentStores`, not just logs: for a fresh single-store controller with injected load failure, assert zero attached stores and unavailable state; a valid disk-backed fixture attaches exactly one store of its expected type; no production failure attaches `NSInMemoryStoreType`. Exercise the explicit `storeURL` failure path too. Do not fix only a test-URL guard: remove the production fallback itself. Assert explicitly requested ephemeral configuration separately without assuming the existing `/dev/null` fixture is an `NSInMemoryStoreType` store.

**Exit gate:** failure remains actionable and distinct from empty results at UI and service boundaries; no persistent data is replaced and no ephemeral save can be reported as durable. Compare repeated healthy cold/warm launches with the Phase 0 baseline on the same build configuration/device: no new required user action, stuck loading state, duplicate service startup, or material launch regression. Record timings and investigate regressions before delivery; do not claim zero latency cost from source inspection.

### Phase 3 — Restart and partial-operation recovery

- Implement `PersistedJobStatusDecoder`: explicitly accept existing title-case statuses and the known legacy lowercase `queued`; inventory other historical spellings before accepting them. Keep the writer's canonical encoding aligned with the reader. Audit how the runtime `.ready` state is persisted rather than assuming it is an existing persisted spelling.
- Replace the loader's `default: .queued` with an unsupported decode result. Retain the original row/raw value and expose a recovery issue outside the runnable queue. This is logical quarantine, not deletion or silent omission. Missing required job fields also produce a visible issue. Do not invent a persisted `quarantined` string an older build will interpret as queued.
- Known persisted `Processing` remains interrupted; completed, failed, cancelled, and interrupted retain their semantics. Unknown/corrupt jobs never auto-run. A user-directed retry must validate input/provider settings and create an explicitly valid attempt before enqueueing; a raw status rewrite alone is insufficient.
- Define a transition table per operation with stable operation ID, attempt ID if needed, required committed artifacts, retry policy, and cleanup owner. Completion requires committed output; a cleanup/finally path is not completion.
- Cover crashes after output creation but before metadata save, after output save but before job completion, and after completion but before source cleanup/acknowledgement. Where output/job state can share one Core Data transaction, prefer that; otherwise reconcile by durable identity.
- Reuse recorder interruption/session fences and salvage paths. A terminated recording cannot be resumed as the same live capture; recover/finalize valid captured media or retain it with a recovery error.
- Fence cancelled, superseded, or deleted jobs/recordings against late callbacks. Repeated launch must not start multiple workers for the same operation.
- Preserve retryable failed-job state until its artifacts and pending effects are resolved or explicitly discarded. Do not use blanket completed/failed-job deletion as recovery.
- Persist only the minimal operation state needed to resolve a demonstrated crash gap. Document location, atomic-write method, retention, protection, and recovery owner for any non-Core-Data receipt. Do not rely on a new row in an unavailable store to retain incoming media.

**Tests:** canonical statuses, known lowercase `queued`, missing/unknown/corrupt values, repeated quarantine across relaunch without enqueueing, and the `.ready` persistence policy; deterministic injected failures at each transition; fresh manager/context after reopening a disk-backed store; repeated recovery; duplicate callback; cancellation/deletion during work; already committed output with unfinished job; missing/inaccessible media. Exceptions simulate boundaries but do not prove process termination: add a controlled terminate/relaunch test with a disposable library.

**Exit gate:** each touched operation has a transition table and durable restart evidence. Uncertain remote results require a documented retry policy, and unresolved cases retain recoverable artifacts rather than claiming success.

### Phase 4 — Media, import, and archive safety

Apply one shared publication contract where appropriate, reusing `RestoredAudioFileInstaller` or other existing helpers only after checking their guarantees:

1. Acquire access and an app-owned copy before external temporary access expires. Keep security-scoped access balanced through the actual copy/read; request renewed access for unusable bookmarks.
2. Create an operation-owned staging file on the destination volume. Bound transfer sizes and cancellation. Validate the applicable format, readable audio track/duration where required, and expected size/integrity when known. Never apply audio rules to transcript/document files.
3. Publish through a same-volume atomic operation without overwriting unrelated content. Cross-volume transfer needs destination-volume staging. Atomic visibility alone does not prove power-loss durability; scope claims to measured behavior.
4. Save metadata using the Phase 2 acknowledgement. If the destination already exists, verify identity and integrity before reuse; quarantine/report conflicts rather than replacing a valid file blindly.
5. Release owned source/staging state or acknowledge delivery only after commitment. Preserve enough durable identity to reconcile a crash between publication and metadata save; retain the published file if save fails.
6. Reconcile abandoned operation-owned files against references and active operations. Retry failed cleanup, use a grace/quarantine policy where appropriate, and never recursively sweep unrelated user media.

Flow order: recording finalization and salvage; Watch intake and sender acknowledgement; Share/Inbox; document-picker audio/video; web imports; transcript/document imports; archive reads/restores and file renames that change persisted URLs. Phase 0 may reorder by demonstrated risk, but each flow needs an explicit disposition before release.

Archive moves need their own crash table: a cross-volume “move” is copy/validate/publish/save/cleanup, and a stale bookmark or disconnected volume is not proof of deletion. Preserve existing archive functionality; this phase adds no new export/restore format.

**Tests:** short/partial transfer; cancellation; existing valid destination; conflicting destination; invalid file; permission/disk-full injection; failed metadata save; crash at each contract boundary; failed cleanup; duplicate Watch/Inbox delivery before and after relaunch; disconnected archive source; unreadable reference inventory. Assert exact file retention/deletion as well as reopened metadata.

**Exit gate:** each changed flow has a source-to-acknowledgement trace, focused filesystem tests, and a demonstrated retry path. Background expiration leaves recoverable work; no assumption is made that iOS will finish or automatically reschedule it.

### Phase 5 — Custom CloudKit integration

- Preserve the existing pending mutation outbox and content-index conflict/retry behavior. A local save is not a cloud acknowledgement, and sync is not a complete device backup.
- Reconcile inbound restores with stable IDs and deletion/local-only policy. Define precedence when deletion, restore, and revive overlap using existing timestamp/identity semantics; do not silently change the conflict model.
- Only acknowledge the matching successfully submitted outbox mutation. An older completion must not erase a newer intent. Retain retryable intent across transient errors and relaunch.
- Coordinate cleanup with restores and local saves. Distinguish cloud absence, network/account failure, and unavailable local/external media. Keep “Keep on This Device” behavior intact.
- Test local commit/cloud failure and cloud success/local acknowledgement failure independently. Preserve duplicate/conflict handling for partially successful batches.
