## Compatibility and artifact ownership

The decision was recorded in
`docs/v3.0-reliability-hardening-phase0.md` before
`MediaOperationRecoveryStore.swift` was added. The model remains unchanged.

- Receipts are version 1 JSON under the app-owned Application Support
  `MediaOperationRecovery` directory; operation staging is under its bounded
  `Staging` child. Paths in receipts are relative and bounded.
- Receipts contain a stable operation UUID, flow, phase, optional recording ID,
  bounded source name, source size/fingerprint, and published-artifact
  size/fingerprint. Source and artifact identities are separate so transcript
  text cannot be confused with generated dummy audio. Receipt writes are atomic
  and file-protected.
- The old app ignores the private receipt directory and can still open the
  unchanged store. A new app retains malformed, unknown, ambiguous, missing,
  or identity-mismatched receipts and owned artifacts for explicit recovery.
  Rollback requires quiescing media operations and preserving the existing
  SQLite/WAL/sidecars, Documents files, receipts, staging, bookmarks, and
  provider-owned sources; it does not require or perform a model rollback.
- Picker/provider URLs, Share/Inbox files, and Watch sender payloads are
  borrowed. D never deletes or modifies them during staging or validation.
  App-owned staging is removed only on verified pre-publication failure or
  after a committed operation is closed. A published local file is retained
  when metadata saving fails.
- Metadata commitment precedes source cleanup, Share-token removal, Watch
  acknowledgement, and archive-source deletion. Archive locations remain
  provider/user-owned. No receipt is uploaded, interpreted as a processing
  job, or used to repeat an uncertain provider request.

## Implementation and test seams

`MediaOperationRecoveryStore` centralizes receipt creation, staging, atomic
no-replace publication, identity verification, phase transitions, and bounded
reconciliation. The test-only persistence-save injection from B2 is reused;
the normal library and real cloud account are not targeted. The focused tests
cover:

- existing-destination conflict without overwrite;
- staged conflict that cannot be reconciled as a committed publication;
- retained published bytes across a reopened store until reference verification;
- corrupt receipt retention and no reference-check callback;
- Share-token validation without consumption;
- failed audio metadata save, retained published file/receipt, relaunch, and
  explicit same-identity retry with source cleanup only after acknowledgement;
- failed transcript save, retained dummy audio/receipt, reopen, and explicit
  retry without a second recording/transcript;
- Watch delivery across receiver recreation, reuse of the published operation,
  stable sender identity, commitment, and post-ack duplicate suppression.

The tests do not simulate a real process kill or claim power-loss durability.
The receipt phase/identity rules are intentionally conservative at those
boundaries: an uncertain attempt is retained rather than replayed or treated as
success.

## Review corrections and superseding validation

- Transcript operations allocate and write their recording UUID before the first
  recording save. Legacy receipts with no UUID resolve an existing row by their
  verified published URL before creating anything.
- Successful transcript and video operations retain compact committed receipts
  for deduplication. `finish` removes their staging only; launch reconciliation
  preserves their committed identity. This closes the gap between metadata save
  and borrowed-source acknowledgement. Identical explicit redelivery returns the
  existing result. A committed receipt whose recording is missing still fails
  closed; evidence is not silently erased by age. Retention is intentionally
  unbounded until an explicit future receipt-discard policy is implemented.
- One malformed or unknown receipt is retained and logged without stopping
  unrelated source lookups. Valid matching ambiguity and artifact mismatch still
  throw, and publication never replaces a destination.
- Audio retry publishes validated staging when publication has not occurred.
  Video imports now record source size/hash and check retained operations before
  exporting; retries finish existing output locally.
- Helpers and same-file extensions replace the new oversized methods/types.
  Archive copy coordination and URL utilities moved into a target-included
  extension. No lint baseline or suppression changes were made.

Added coverage exercises staging-only audio/video retry with an unrelated
corrupt receipt, source identity allocated before transcript save, legacy missing
identity recovery, and committed transcript redelivery after reconciliation.
The video retry test supplies a retained exported-audio fixture and verifies the
retry avoids export; it does not claim real provider video export qualification.
The first review run failed the obsolete test expectation that a committed
