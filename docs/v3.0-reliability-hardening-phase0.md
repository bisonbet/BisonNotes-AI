## C compatibility decision — recorded before recovery-state implementation

Date: 2026-09-13
Decision owner: current `v3.0-reliability-hardening` implementation
Decision: reuse the existing `ProcessingJobEntry` row and its `status`,
`error`, `completionTime`, stable `id`, and existing job metadata. Do not add a
Core Data entity/attribute, model version, persistent-history requirement, or a
separate operation-receipt format for slice C. The existing B2 tagged
`modelName` envelope remains unchanged and is not extended for recovery.

The compatibility reason is concrete: the pre-C reader accepts the existing
title-case statuses but routes an unknown raw value through its `default:
.queued` path. C therefore must never persist a new `quarantined` status string.
The C reader will accept the verified durable title-case values plus the
legacy lowercase `queued`, and will return an explicit unsupported result for
`Ready`, unknown, or missing status values. The source/history audit found no
production Core Data writer for `Ready`: `.ready` is the manager's in-memory
initial state, not an established persisted spelling. On first read of an
unsupported value, C retains the job row and stable identity, records the
bounded original raw value in an existing `error` recovery marker, and
persists the known terminal `Failed` status. This makes an older reader see a
non-runnable failed job while the new reader reconstructs and re-presents the
recovery issue. If that quarantine save fails, the raw row remains untouched
and is withheld from all runtime execution; the failure remains a
downgrade/release qualification blocker rather than being silently treated as
queued.

The compatibility inventory supports that boundary: the comparison-parent
`CoreDataManager.createProcessingJob` writer stored lowercase `queued`, while
the comparison-parent loader explicitly recognized only `Queued`,
`Processing`, `Completed`, `Failed`, `Cancelled`, and `Interrupted`; its
fallback was the unsafe `.queued` case. A production-source/history search
found no `JobProcessingStatus.ready` assignment or Core Data write of `Ready`.

Old/new reader and writer behavior:

- Existing writers continue to represent durable job states with the
  canonical title-case spellings (`Queued`, `Processing`, `Completed`,
  `Failed`, `Cancelled`, and `Interrupted`). New job creation will use
  canonical `Queued`; the lowercase `queued` spelling remains a read-only
  compatibility case for rows written by older builds. The runtime `.ready`
  state is not accepted from Core Data because no production writer for
  `Ready` was found.
- A persisted `Processing` value decodes as the known in-flight state and is
  reconciled to `Interrupted` on restart; completed, failed, cancelled, and
  interrupted rows retain their meanings. Unknown/corrupt rows never enter
  the active runnable list.
- Missing required job fields produce a visible recovery issue and retain the
  original row. A row without a stable identity cannot be rewritten, so it is
  withheld and remains an explicit qualification case.
- The recovery marker is bounded and diagnostic-only; it contains no transcript,
  credential, or unredacted path data. Recovery does not delete the job,
  recording, source audio, sidecars, or pending cloud intent. Explicit user
  cleanup may discard a resolved terminal row; automatic restart/cleanup may
  not use an unsupported decode as proof that work is complete.

The marker format is fixed before implementation as
`bisonnotes-recovery-v1:<base64(JSON)>`, where the version-1 payload contains
only a bounded reason and bounded original `rawStatus` (or an explicit missing
sentinel). It is stored in the existing `ProcessingJobEntry.error` field; it is
not a new receipt, column, or model value. New readers recognize the marker and
reconstruct the recovery issue, while older readers see only the known
terminal `Failed` status.

Rollback and tests: because C writes only an existing known terminal value and
keeps the original raw value in the existing error field, an older reader will
not auto-run a successfully quarantined row. A failed quarantine write leaves
an unknown raw value, so downgrade is not permitted until that row is resolved
or a tested repair is applied. Tests must cover canonical and lowercase
decoding, unknown/missing values, durable marker persistence and repeated
recovery after reopening, old-reader-safe status values, no execution or
cleanup from quarantined rows, and failure of the quarantine save. No model
file is to be edited for C.

### C review amendment — uncertain prior attempts require review

The source review found that B2 save ordering does not identify committed
output after termination between output save and job completion. Until a
versioned durable attempt/output association exists, C must not automatically
replay persisted `Processing` or `Interrupted` jobs. The decoder still
recognizes both values; the loader retains their original status in the
existing recovery marker and writes canonical `Failed`, with a visible review
issue. This supersedes the automatic restart disposition above. No provider
call, output overwrite, or source cleanup is authorized by that recovery state.
The user may inspect retained output and intentionally start a new attempt
through the existing validated entry point. Same-session live interruption
handling remains separate from restoring a prior process's job.

Recovery identities are excluded from both legacy-message resume and queued
execution. Existing valid markers are read before required-field validation,
so repeated launch preserves the original evidence even for malformed rows.
Terminal cleanup returns identities from its deletion transaction; UI recovery
issues are removed only for rows actually deleted. Failed deletion retains both.

## D compatibility and artifact-ownership decision — recorded before media recovery state

Date: 2026-09-13
Decision owner: current `v3.0-reliability-hardening` implementation
Decision: keep the Core Data model and all existing recording/archive fields
unchanged. Add a version-1, app-private media-operation receipt only for the
demonstrated publication-to-metadata-save crash gaps. Receipts live under
Application Support in an app-owned recovery directory; media staging lives in
an app-owned sibling directory on the app container's destination volume.
Receipt writes are atomic and file-protected. The receipt records an operation
UUID, flow kind, bounded phase, bounded source display name, and relative
staging/published paths plus exact source and published-artifact size/fingerprint
when available; it does not store provider credentials, transcript content, an
absolute path, or a cloud mutation. No receipt is uploaded or interpreted as a
processing job. Source identity and published-artifact identity are separate so
a generated transcript audio file cannot be mistaken for its text input. Watch
recovery additionally keys a retry to the sender's stable recording UUID, so a
filename change cannot create a second destination for the same delivery.

Compatibility is deliberately additive outside the model. Existing
`RecordingEntry` URLs, `RecordingArchiveLocationEntry` rows/bookmarks, Share
tokens, Watch processed-ID tracking, and the existing recording recovery and
export staging formats remain readable. An older app ignores the private
receipt directory and sees only a published Documents file if a newer build
had already made one visible; it must not be expected to reconstruct the
receipt. A newer app treats a missing, malformed, or unknown receipt as
unresolved evidence and retains it and any owned artifact. No new Core Data
status, model version, uniqueness constraint, persistent-history requirement,
or import/migration entry point is introduced. Rollback therefore requires
quiescing media operations and preserving the existing store and Documents
files; receipt cleanup is a new-build operation and is not a downgrade
precondition. An orphaned published file is retained for manual recovery, not
silently deleted during downgrade.

The ownership contract is per boundary:

- External picker/provider URLs, Share/Inbox source files, and Watch sender
  payloads are borrowed until the local operation commits. The app never
  deletes or modifies a borrowed source as part of staging or validation.
- A receipt and its staging artifact are app-owned. Staging is created before
  the copy/export begins, is bounded to a known directory and operation UUID,
  and is removed only on a verified pre-publication failure or after the
  committed operation is closed. A crash leaves it discoverable; launch
  reconciliation may retain it or move it to a bounded recovery disposition,
  but never sweeps unrelated user media.
- A published local recording is app-owned once it is atomically visible. It
  is never removed because metadata save failed. A successful Core Data save is
  the metadata commitment; only after that commitment may an Inbox/Share
  source be acknowledged, a Watch transfer be confirmed, or an explicitly
  requested archive source be deleted.
- Archive destinations remain user/provider-owned. Archive metadata is saved
  only after the selected file is present and passes the applicable audio
  identity/readability checks. Restore uses a non-overwriting publication
  boundary; a conflict is reported and the valid destination is left intact.
- Transcript/document imports use generic file ownership and text/document
  validation. They never route a document through audio validation. A dummy
  audio file for a transcript is retained until both the recording and
  transcript metadata saves are acknowledged.

On relaunch, reconciliation is intentionally filesystem- and reference-only:
it checks owned receipt paths against active operations and existing recording
URLs, removes a receipt only when the durable reference is verified, and
retains unresolved staging or published files for a later user-directed
retry/recovery. It does not call an AI/provider, re-run a transcription job,
overwrite output, consume a Share token, acknowledge Watch delivery, delete an
external archive source, or infer success from an empty/missing read. This
preserves C's rule that uncertain prior processing attempts remain non-runnable.
Each disposition emits the bounded `staging_reconciled` diagnostic event with
the operation kind and disposition, never a filename.

The D test contract covers: copy/export failure and partial staging, existing
valid and conflicting destinations, invalid/unreadable media, save failure
with retained published bytes, failed cleanup, corrupt/unknown receipts,
closing and reopening a disk-backed store with a retained artifact, Watch
duplicate delivery before and after relaunch, Share/Inbox token retention
until source acknowledgement, disconnected archive sources, and a recovery
pass that performs no provider call. Rollback evidence must show the old model
opens unchanged and that the selected store, source files, published files,
sidecars, and archive bookmarks remain intact. Signed Watch, background
expiration, provider/file-provider, and physical-device checks remain runtime
qualification gates; this decision does not make A/B1/B2/C or D
release-qualified.

### D review amendment — source acknowledgement and receipt identity

Transcript recording UUIDs are allocated in the receipt before metadata writes.
Completed transcript/video receipts remain a compact local deduplication record
across acknowledgement and relaunch, with staging removed. They are not expired
by age. Missing committed references require review; automatic resurrection is
withheld. This supersedes any earlier unconditional receipt-close statement.
Unrelated corrupt receipts are retained individually rather than disabling all
intake. Valid matching ambiguity remains non-runnable. No receipt schema version
or Core Data model change was required; existing version-1 optional IDs/hashes
remain readable. Older video receipts lacking source hashes cannot safely match
and remain unresolved rather than being guessed as an exact retry.
