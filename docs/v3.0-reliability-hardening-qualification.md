## Failure investigation

The failures were investigated from the result bundles, simulator diagnostics,
and source rather than hidden with a retry or baseline.

1. The first direct full iOS attempt failed before test bootstrap because the
   unsigned UI-test host constructed `CKContainer` without the iCloud entitlement.
   The crash was `EXC_BREAKPOINT`/SIGTRAP in `CKContainer`, through
   `iCloudStorageManager.initializeCloudKit`. The UI test's
   `--disable-cloud-services` default was applied after the manager initializer
   had already scheduled initialization.
2. The first post-fix full run reached 306 planned tests, with 299 passing and
   seven failures. Six unique tests still reached `CKContainer`: setting the
   persisted `iCloudSyncEnabled` value during fake-transport construction invoked
   the `isEnabled` observer and started real CloudKit. The Phase 6 guard now
   requires both a real transport and no disable argument before that path can
   start. The isolated six-test follow-up passed 6/6.
3. The final unsigned full iOS run reached all 658 aggregate tests. Its only failures were
   these `KeychainSecretStoreTests`:

   - `testCreatesAndUpdatesKeychainSecret()`
   - `testDeletesKeychainSecretAndTreatsMissingItemAsSuccess()`
   - `testEmptyStringDeletesKeychainSecret()`
   - `testMigratesStringSecretsFromUserDefaultsToKeychain()`
   - `testRemovesLegacyAWSSecretsFromUserDefaultsAndKeychain()`
   - `testSuccessfulMutationsAdvanceSecretRevision()`

   The mutation failures report Keychain status `-34018`, and the migration test
   reports an assertion failure after the unsigned simulator cannot perform the
   entitled Keychain operation. The run used `CODE_SIGNING_ALLOWED=NO`; this is
   not evidence that credential behavior should be weakened.

4. The isolated signed Keychain run above passed all six tests. No Keychain
   implementation or test behavior was changed. This resolves the unsigned
   simulator-only Keychain result for the disposable signed-simulator gate, but
   it does not replace physical-device provisioning evidence.

5. The first full signed iOS attempt failed before test execution while signing
   `BisonNotes AI.debug.dylib`; its result bundle records `unknown` and 0 tests.
   The one environment-adjusted pre-fix full execution with
   `ENABLE_DEBUG_DYLIB=NO` then ran the suite and failed one accessibility audit.
   The exported issue was `Dynamic Type font sizes are unsupported` for the
   element `Recommended for normal use. Offline VBx estimates the number of
   speakers and does not impose a two- or three-speaker cap.` Its detailed
   description says the user will not be able to change the font size of that
   SwiftUI accessibility node. The existing test exception list recognized this
   same element only as `Dynamic Type font sizes are partially unsupported`;
   that historical failure and attachment are retained at
   `/private/tmp/bisonnotes-v3-phase6-accessibility-all-attachments/35F6632E-DA1C-4DD1-863B-97B42F1E0A90.txt`.

6. The demonstrated defect was the missing vertical expansion on the multiline
   explanatory `Text` in `FluidAudioSettingsView`, not a reason to broaden the
   audit exception. Adding only `.fixedSize(horizontal: false, vertical: true)`
   made the focused accessibility test pass. Its accessibility-size screenshot
   shows all three lines of copy inside the scrollable settings content with no
   visible clipping, and the full post-fix signed run passed all 658 aggregate
   tests.

The incomplete XcodeBuildMCP attempt and the pre-fix crash runs are retained as
diagnostic history but are not counted as passing qualification runs. Automatic

## Disposable-library fixture contract

No persistent fixture library was added to the repository. The tests create
per-test temporary roots and clean them up. The following is the reproducible
fixture shape for any manual or scripted Phase 6 work:

```text
/private/tmp/bisonnotes-v3-phase6-fixture.<random>/
├── store/
│   ├── library.sqlite
│   ├── library.sqlite-wal                 (when present)
│   └── library.sqlite-shm                 (when present)
├── Documents/
│   ├── apprecording-<timestamp>-<UUID>.m4a
│   ├── Inbox/                             (share/import fixture, when present)
│   ├── SummaryAttachments/<summary-UUID>/ (when present)
│   └── deferred-recovery.json             (when present)
├── Application Support/
│   └── MediaOperationRecovery/
│       ├── media-operation-<UUID>.json
│       └── Staging/
├── backup/
└── manifest/
```

For a durable Core Data fixture, create a fresh directory and construct
`PersistenceController(storeURL: fixtureRoot/store/library.sqlite)`. For
in-memory behavior, use `PersistenceController(inMemory: true)` and verify that
the test cannot pass `requireDurableStore()`. Construct
`MediaOperationRecoveryStore` with the fixture's recovery and Documents URLs;
do not use `MediaOperationRecoveryStore.live()` in a fixture test. Seed only
synthetic UUIDs, a short valid audio fixture, metadata, transcripts, summaries,
and SHA-256/file-size identities. Record the fixture root, app build, model
version, and hashes in its manifest. Remove or quarantine only that exact root
after the test.

Existing automated fixture coverage demonstrates this setup:

- `ICloudBackupRegressionTests` and `ICloudSyncOrchestrationTests` use in-memory
  Core Data, temporary directories, and `FakeCloudKitTransport`.
- The SQLite migration, deletion/outbox reopen, and save-failure rollback tests
  use explicit temporary `storeURL` values.
- `MediaOperationRecoveryTests` construct recovery and Documents roots directly,
  then exercise staged, published, metadata-pending, reconciliation, integrity,
  and receiver-recreation behavior.
- `Swift6PersistenceIsolationTests` verify durable readiness, no in-memory
  fallback, reopen behavior, recovery markers, failed saves, and Watch retry
  identity.

This gives a disposable library without connecting a test to the user's normal
Application Support/Documents roots or a CloudKit account.

## Store, WAL, sidecar, media, receipt, and rollback procedure

Use this procedure for every disposable snapshot or rollback. It is also the
minimum evidence package for a future signed-device run.

### Preserve

1. Record the exact app build, source SHA, model/schema version, device OS,
   entitlements, fixture/account identifier, and operation boundary.
2. Quiesce writers: finish or explicitly mark the operation, stop sync and
   background work, wait for Core Data saves and receipt writes, then close the
   app/store. Do not copy an active SQLite store as if its main file were complete.
3. Copy the entire persistent-store set together: the base
   `BisonNotes_AI.sqlite` (or the URL reported by the persistent-store
   coordinator), `-wal`, `-shm`, and every same-store companion/sidecar matching
   `*.sqlite-*` when present. Never preserve only the main SQLite file while a WAL
   exists.
4. Preserve app-owned media and recovery state together:

   - the complete Documents media tree, including `apprecording-*.m4a` and
     imported files;
   - `Documents/Inbox` and `deferred-recovery.json` when present;
   - `Documents/SummaryAttachments`, including each `metadata.json` and `files`
     directory;
   - Application Support `MediaOperationRecovery`, its `Staging` directory, and
     all `media-operation-<UUID>.json` receipts;
   - `Recording Recovery`, `ArchiveStaging`, and `AudioExportStaging` only when
     an active test operation owns artifacts there; and
   - any active failure artifact explicitly named by the operation manifest.

   The `PendingCloudMutation` outbox is a Core Data entity in the same SQLite
   store, not a separate safe-to-copy JSON queue. Legacy UserDefaults queue keys
   may be migration evidence, but they do not replace the store/WAL snapshot.
   Do not copy Keychain secrets into a filesystem fixture. Downloaded models,
   caches, and ordinary temporary files are not library state.

5. `iCloudAudioStaging/<runIdentifier>` and `WatchTransferStaging` are temporary
   run-scoped locations. Capture an active file there only as failure evidence
   before cleanup; a normal rollback relies on the durable Documents media,
   recovery receipt, and Core Data state. Do not treat a cleaned temporary upload
   copy as the library's source of truth.
6. Preserve file permissions, protection attributes, extended attributes, and
   ACLs where the platform export permits. Generate a manifest containing every
   relative path, byte size, modification time, and SHA-256 fingerprint. Keep the
   failed snapshot beside the good snapshot until review is complete.

### Roll back

1. Stop the disposable app and quiesce all writers. Do not attempt a local
   rollback while a CloudKit mutation is in flight.
2. Move the failed disposable root to a recoverable, timestamped quarantine
   directory. Do not delete it until the incident is closed.
3. Restore the base SQLite file, WAL, SHM, sidecars, Documents media, and
   Application Support recovery/receipt directories as one versioned set. Restore
   into a temporary sibling first, validate the manifest, then replace the target
   root with an atomic directory move where the platform permits.
4. Reopen with the exact model-compatible app build. Verify store readiness,
   record IDs and relationships, media fingerprints, receipt phases, pending
   outbox rows, and the absence of duplicate publication. Retain the failed
   artifacts and result bundle in the quarantine directory.
5. A local restore cannot undo CloudKit records, tombstones, assets, or
   acknowledgements already accepted remotely. Any remote rollback is a separate
   approved operation against the disposable CloudKit environment; it is never an
   implicit consequence of copying SQLite files.
