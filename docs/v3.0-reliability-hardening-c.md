## Scope and compatibility decision

The compatibility decision was recorded at the end of
`docs/v3.0-reliability-hardening-phase0.md` before the C source changes. C
reuses the existing `ProcessingJobEntry` row, stable `id`, `status`, `error`,
`completionTime`, and existing job metadata. It adds no Core Data entity,
attribute, model version, persistent-history requirement, or separate receipt.
The existing B2 `modelName` envelope is unchanged.

The old reader's unsafe behavior was specific and bounded: an unrecognized
status reached its `default: .queued` branch. C therefore never writes a new
status spelling such as `quarantined`. It writes the existing canonical
`Failed` spelling and stores a bounded, versioned recovery marker in the
existing `error` field. An older reader sees a known terminal `Failed` row and
cannot auto-run it; the new reader reconstructs the recovery issue and retains
the row for review. If the quarantine save fails, the original raw status and
row remain untouched, and processing is withheld for the session.

The marker is `bisonnotes-recovery-v1:<base64(JSON)>`. Its version-1 payload
contains only a bounded reason and bounded raw status, using `<missing>` for a
missing raw status. It contains no transcript, credentials, or unredacted
paths. This is diagnostic recovery state, not a new persistence schema.

## Transition and crash-boundary table

`ProcessingJob.id` is the stable operation identity. C does not add a separate
attempt identifier: an intentional rerun through the existing start entry
point creates a new `ProcessingJob` UUID, while an interrupted or quarantined
row retains its original identity. `regenerationSummaryIds` continues to own
the existing summary-replacement association.

| Transition | Required durable evidence before advancing | On failure or relaunch | Cleanup/side-effect owner |
| --- | --- | --- | --- |
| enqueue → `Queued` | Recording identity lookup succeeds and `createProcessingJob` saves the row. | Do not append to `activeJobs` or start work. The source and prior job remain available. | `BackgroundProcessingManager` enqueue path. |
| `Queued` → `Processing` | The processing-state update saves before a worker task is launched. | Leave the prior durable state visible, set a load/start error, end the background task, and do not execute. | `processNextJob`. |
| `Processing` → output persisted → `Completed` | Transcript/summary output save succeeds before the final job update; final `Completed` save succeeds before success notification. | A failed output save is a failed job with source/artifacts retained. A failed completion save withholds success and source cleanup. | B2 workflow/job save boundaries; `processNextJob`. |
| `Completed` → notification/source cleanup | The terminal job state is already committed. | Notification or post-commit filesystem cleanup may be retried without undoing committed metadata. | Existing post-commit cleanup path. |
| `Processing` → `Interrupted`/`Cancelled`/`Failed` | The replacement job state saves before the corresponding notification or retry disposition. | Keep the last committed state and recoverable source when the state save fails; no false terminal acknowledgement or cleanup. | Existing cancellation, termination, and stale-job paths. |
| persisted unknown/missing/corrupt → recovery | Existing row ID plus canonical `Failed` and bounded marker save successfully. | Preserve raw row, expose non-durable recovery issue, set `jobLoadError`, and withhold all execution. | C loader and `quarantineProcessingJob`. |
| recovery → explicit user cleanup | User selects cleanup and the throwing delete completes. | Keep the issue and row when deletion/read fails. | Existing manual cleanup only; startup never treats the issue as completion. |

B2 ordering establishes save acknowledgement but does not alone reconcile a terminated attempt. C review now withholds automatic replay of prior-process `Processing`/`Interrupted` jobs; it does not claim resumable output persistence or automatic recovery:

- output created before metadata save: failed metadata persistence retains the
  output/source recovery inputs;
- output metadata committed before job completion: the final job save remains
  the completion acknowledgement, so a failure cannot emit success or release
  the source; and
- completion committed before source cleanup: cleanup is post-commit and
  cannot turn a committed job back into an uncommitted one.

No process-termination claim is made by exception injection. Controlled
termination and signed runtime behavior remain qualification work.

The DEBUG-only tests use disposable in-memory or temporary disk stores and the
existing injected Core Data seams. They do not touch the normal library or a
live CloudKit account.

- `testPersistedJobStatusDecoderAcceptsOnlyDocumentedValues` covers the

  `Queued` writer policy.
- `testUnsupportedPersistedJobIsQuarantinedAndReappearsAfterReopen` verifies
  stable identity, canonical old-reader-safe status, preserved raw status in
  the marker, repeated issue presentation, and no queue admission after a
  disk-store reopen.
- `testPersistedProcessingJobRequiresReviewBeforeReplay` covers
  non-runnable restart disposition through the production resume path.
- `testMissingRequiredJobFieldIsQuarantinedAndNotRunnable` covers a missing
  provider field without fabricating a runnable job.
- `testMissingPersistedJobStatusIsQuarantinedAndNotRunnable` covers a missing
  status, including the bounded missing-status marker and non-runnable
  projection.
- `testQuarantineSaveFailureRetainsRawJobAndWithholdsProcessing` verifies the
  raw row is unchanged and execution is withheld when durable recovery cannot
  be written.
- `testCorruptRecoveryMarkerIsRequarantinedAndNotRunnable` verifies malformed
  durable recovery state remains visible and non-runnable.
- The existing A/B1/B2 focused tests continue to cover throwing collection
  reads, save acknowledgement, cleanup/cloud/read-failure gates, durable
  reopen, Watch retry, and preservation of unrelated pending edits.

## C review corrections

All four source-review findings were addressed:

- Recovery identities are excluded from legacy failed-message resume and queue
  execution. Status text such as `interrupted_v2` cannot cause a provider retry.
- Restored `Processing` and `Interrupted` attempts require review. The current
  schema cannot prove which output belongs to the unfinished attempt; retaining
  output and withholding replay is the selected conservative policy. Automatic
  attempt/output reconciliation remains unimplemented and is not claimed.
- Valid existing quarantine markers are restored before required-field checks,
  preserving original status evidence across repeated disk-store reopen.
- Cleanup reconciles the exact identities deleted in the durable transaction,
  including malformed jobs with no `activeJobs` projection. Failed cleanup
  preserves the row and issue; cancelled rows are not silently removed from UI.

Regression coverage includes production resume/queue calls for malicious-looking
status text, a disk-backed committed transcript/summary plus unfinished jobs,
malformed-marker preservation across reopen, and failed/successful cleanup.
The prior-process tests do not simulate physical process termination; they
construct its durable boundary state and reopen it. Hardware gates remain.
